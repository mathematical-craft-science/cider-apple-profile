# Доменный backlog

## Выбор сортов яблок для sugar-acidity plot

Нужно спроектировать модель фильтрации и выбора точек sugar-acidity zone для
`AppleVariety`.

Количество сортов яблок может стать очень большим, поэтому порт вида
`List<@NonNull AppleVarietySugarAcidityZoneAssessment> list()` не подходит как
долгосрочная форма загрузки данных для графика. Графику чаще нужен осмысленный
набор сортов, а не весь каталог целиком.

Возможные направления:

- Query object для точек сортов яблок на графике, например
  `AppleVarietySugarAcidityZonePointQuery`.
- Фильтрация по sugar-acidity zone.
- Фильтрация по уровням sugar, acidity и tannin.
- Поиск по названию сорта или синониму.
- Фильтрация по сезону созревания, происхождению, стране/региону или сидровой
  традиции.
- Фильтрация по полноте и надежности измерений.
- Явный выбор по ids сортов.
- Pagination или cursor-based загрузка.
- Сортировка по названию, зоне, sugar, acidity, tannin или релевантности.
- Опциональная загрузка по viewport, если график станет интерактивным.

API и application port в итоге должны выражать эту модель выбора, а не
предоставлять неограниченную операцию `list()`.

## Сезоны и партии для feedstock samples

Для `FeedstockSample` нужно предусмотреть возможность указывать сезон и партию.
Это важно для выборки точек на графике: химический профиль сырья зависит не
только от сорта, но и от конкретного урожая, поставки, хранения и момента
измерения.

Возможные характеристики `FeedstockSample`:

- Сезон урожая.
- Партия или batch.
- Cider maker / владелец сырья.
- Дата сбора.
- Дата прессования или измерения.
- Условия хранения перед измерением.
- Источник сырья: свой сад, поставщик, ферма, рынок.

## Возможные характеристики apple varieties

Для `AppleVariety` стоит отделять устойчивые сортовые характеристики от
характеристик конкретного урожая или партии. В контексте cider-домена здесь
нужны прежде всего признаки, которые помогают оценивать сидровой потенциал
сорта, искать кандидатов для графиков и приводить химический профиль к
понятным локальным терминам.

Возможные характеристики:

- Синонимы и локальные названия.
- Страна, регион или сидровая традиция происхождения.
- Сезон созревания: ранний, средний, поздний.
- Рекомендуемый период хранения перед прессованием.
- Основное назначение в контексте сидроделия: single-variety cider, blending,
  fresh juice, cooking cider, vinegar, distillation.
- Cider classification по локальным системам: English, French, Spanish,
  North American.
- Типичный sugar-acidity zone.
- Типичный диапазон sugar, acidity, tannin и pH.
- Надежность химического профиля: единичное измерение, диапазон, статистика,
  источник данных.
- Описание вкусового/технологического вклада в сидр: body, sharpness,
  bitterness/astringency, aroma intensity.
- Роль в профиле сидра: sugar contributor, acid contributor, tannin
  contributor, balancing apple.
- Пригодность для single-variety cider.

Характеристики вроде урожайности, силы роста дерева, времени цветения,
опылителей, устойчивости к болезням, зимостойкости и пригодности к климату
скорее относятся к orchard-домену. Их не стоит смешивать с cider-моделью
`AppleVariety`, пока в системе явно не появится область планирования сада.

## Управление полнотой и актуальностью chemical profile

Неполный `ChemicalProfile` является допустимым состоянием данных. Система должна
позволять загружать и хранить профили, в которых отсутствуют отдельные
измерения: sugar, acidity, tannin, pH или другие будущие показатели.

При этом неполнота профиля должна быть явно видна в тех сценариях, где
конкретная задача требует определенный набор измерений. Например,
sugar-acidity plot требует sugar и acidity, а North American profile требует
sugar, acidity и tannin.

Важно не вводить понятие "полный профиль" как универсальный флаг. Один и тот же
`ChemicalProfile` может быть пригоден для одной задачи и непригоден для другой.
Лучше мыслить через capability assessment: оценку пригодности профиля для
конкретного сценария.

Примеры capabilities:

- `SUGAR_ACIDITY_PLOT`: требует sugar и acidity.
- `NORTH_AMERICAN_PROFILE`: требует sugar, acidity и tannin.
- `CIDER_CLASSIFICATION`: требования зависят от выбранной классификационной
  системы.
- Будущие алгоритмы работы с сырьем могут потребовать sugar, acidity, tannin,
  pH, volume или другие показатели.

Возможная форма доменной модели:

```java
record ChemicalProfileCapabilityAssessment(
    ChemicalProfileCapability capability,
    boolean capable,
    Set<ChemicalProfileMeasurement> required,
    Set<ChemicalProfileMeasurement> present,
    Set<ChemicalProfileMeasurement> missing
) {
}
```

### AppleVariety: качество администрируемого каталога

Для `AppleVariety` неполный химический профиль допустим при загрузке данных, но
это должно становиться частью управления качеством каталога. Каталогом управляет
администратор, поэтому система должна помогать ему видеть проблемные записи и
принимать решение по каждой из них.

Возможные административные сценарии:

- Получить отчет по сортам с неполным chemical profile.
- Увидеть, каких именно измерений не хватает для sugar-acidity plot,
  North American profile или другой задачи.
- Найти данные и дополнить профиль.
- Оставить сорт в каталоге, но исключить его из отдельных аналитических
  представлений.
- Скрыть или исключить сорт из публичного каталога, если данных недостаточно.
- Отметить профиль как ожидающий уточнения или проверки источников.

Для графика это означает, что сорт с неполным профилем не должен молча исчезать
из системы. Даже если он не может быть отображен как точка, администратор должен
понимать причину и видеть это в отчетах о качестве данных.

### FeedstockSample: постепенное заполнение данных сидроделом

Для `FeedstockSample` неполный профиль является нормальным рабочим состоянием.
Сидродел может сначала знать только sugar, затем добавить acidity, позже tannin
или pH. Такие данные не нужно считать ошибочными или непригодными для хранения.

Возможные сценарии для сидродела:

- Создать sample с частичным набором измерений.
- Видеть предупреждение, что sample пока нельзя отобразить на sugar-acidity
  plot.
- Понимать, каких измерений не хватает для конкретного графика или оценки.
- Постепенно дополнять профиль по мере проведения измерений.
- Фильтровать samples по полноте данных, сезону, партии или cider maker.

Для batch endpoint-а графика полезно возвращать не только отображаемые точки, но
и элементы, которые нельзя отобразить. Например:

```json
{
  "points": [],
  "unplottable": [
    {
      "subjectId": "...",
      "subjectType": "FEEDSTOCK_SAMPLE",
      "displayName": "Late season batch A",
      "capability": "SUGAR_ACIDITY_PLOT",
      "requiredMeasurements": ["SUGAR", "ACIDITY"],
      "presentMeasurements": ["SUGAR"],
      "missingMeasurements": ["ACIDITY"]
    }
  ]
}
```

Такой контракт оставляет график простым: он рисует только `points`. Но API при
этом не скрывает неполные данные, а UI может показать предупреждения, отчеты и
подсказки по дальнейшему заполнению профиля.

`SugarAcidityZoneAssessor` не должен решать задачу полноты данных. Его
ответственность - оценить профиль, который уже пригоден для sugar-acidity
assessment. Проверка пригодности профиля должна находиться перед assessor-ом, в
отдельной доменной или application service модели.
